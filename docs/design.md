
# 설계 문서 — 반도체 & 디스플레이 뉴스 AI Agent

## 1. 문제 정의

| 기존 방식의 문제 | Agent가 해결하는 방법 |
| --- | --- |
| 여러 매체를 돌아다니며 기사를 검색·확인하는 데 시간이 많이 듦 | 국내·해외 18개 RSS를 1시간마다 자동 수집 |
| 같은 이슈를 다룬 중복 기사가 많음 | 규칙 기반 1차 거르기 + AI가 같은 사건으로 확인한 기사만 묶어 카드 하나로 |
| 필요한 정보를 고르기 어려움 | 키워드 필터 + AI 관련성 판단, 카테고리·키워드 분류 |
| 무엇이 중요한지 매번 판단해야 함 | AI가 사건 유형을 분류하고, 사용자가 정한 기준표로 코드가 1～5점과 계산식을 매겨 중요한 이슈를 맨 위에 |

## 2. 기능 정의

| ID | 기능 | 입력 | 출력 | 구현 |
| --- | --- | --- | --- | --- |
| F1 | 뉴스 수집 | `config/sources.yaml` | 기사 목록 (제목, 링크, 매체, 시각, 요약문) | `agent/collect.py` |
| F2 | 1차 중복·관련성 거르기 | F1 기사 목록, 이미 본 URL | 중복 제거된 기사 묶음 | `agent/dedupe.py` |
| F3 | 이슈 묶기·분류 (AI) | F2 결과, 진행 중인 이슈 | 기사별 이슈 배정, 카테고리, 관련 여부 | `agent/analyze.py` |
| F4 | 요약·사건 분류 (AI) + 중요도 계산 (코드) | 이슈별 기사, 중요도 기준표 | 헤드라인, 3줄 요약, 태그, 기업, 사건 유형, 직접 당사자, 확정 여부 → 중요도 1～5, 계산식 | `agent/analyze.py`, `agent/score.py` |
| F5 | 저장·보관 | F3·F4 결과 | `data/issues.json`, `state.json`, `runs.json`, `archive/` | `agent/store.py` |
| F6 | 웹 인터페이스 | `data/*.json` | 필터·검색·주요 이슈가 있는 대시보드 | `web/`, `agent/build_site.py` |
| F7 | 주기 실행·배포 | 1시간 주기 (또는 수동 실행) | 데이터 커밋 + GitHub Pages 배포 | `.github/workflows/update.yml` |

## 3. 작업 흐름

```
GitHub Actions가 1시간마다 실행
  ↓
F1  RSS 수집: 최근 48시간 기사
  ↓
F2  1차 거르기: URL 중복 · 제목 유사 · 키워드
  ↓    (남은 기사가 없으면 F6으로 건너뜀)
F3  AI 이슈 묶기: 사건 정리 → 같은 사건 확인
  ↓    (AI 오류가 나면 묶지 못한 기사는 다음 실행으로 미룸)
F4  AI 요약·사건 분류 + 기준표로 중요도 계산
  ↓    (AI 오류가 나면 "요약 대기"로 먼저 게시하고 다음 실행에서 다시 요약)
F5  저장: issues · state · runs
  ↓
F6  웹 페이지 생성
  ↓
F7  데이터 커밋 + GitHub Pages 배포
```

### 단계별 규칙

1. **수집**: 매체마다 독립적으로 처리해서, 한 곳이 실패해도 나머지는 계속한다. 매번 최근 48시간 기사를 모두 보고 이미 처리한 기사만 건너뛰므로, 실행이 늦거나 매체가 잠시 실패해도, 상한 때문에 미룬 기사도 다음 실행에서 처리된다. 시간대가 없는 날짜는 매체 설정의 시간대(국내는 KST)로 해석한다.
2. **1차 거르기** (비용 없음)
   - URL을 정규화(추적용 파라미터 제거)해서 같은 기사와 이미 본 기사를 뺀다.
   - 제목을 정규화하고 글자 단위 유사도가 기준 이상이면서 **언급된 회사가 같을 때만** 한 묶음으로 본다. 다른 회사의 비슷한 제목(예: 각 사의 "3분기 영업이익")이 합쳐지는 것을 막기 위해서다.
   - 일반 매체는 관련 키워드가 있는 기사만 남긴다.
3. **이슈 묶기·분류 (AI)**
   - **확실한 중복만 묶는다.** 한 번에 많은 기사를 보고 묶으면 판단이 흔들려서(다른 사건을 붙이거나 같은 사건을 둘로 나눔) 세 단계로 나눈다.
   - ① AI가 기사 20묶음씩 핵심 사건 한 줄(`event`)과 관련성(`relevant`)을 정리한다. 같은 질문을 3번 묻고 다수결로 정한다. 관련성 기준은 중요도 기준표의 사건 유형과 같다.
   - ② 규칙으로 같은 사건일 수 있는 짝을 고른다: 새 기사끼리, 새 기사와 최근 72시간 이슈. 같은 회사가 나오거나 사건 문장이 비슷한 짝만 (회사가 서로 전혀 다르면 제외, 기사 하나당 최대 5짝).
   - ③ 짝마다 AI가 같은 사건인지 3번 확인하고, **2번 이상 같다고 한 짝만** 한 이슈로 묶는다. 확인되지 않은 기사는 혼자 새 이슈가 된다.
   - 응답은 코드로 검증한다. AI가 빠뜨린 기사는 관련 있음으로 두어 혼자 새 이슈로 남기고, 빠뜨린 짝은 묶지 않는다.
4. **요약·사건 분류 (AI), 중요도 계산 (코드)**
   - 새 이슈, 그리고 다른 매체 기사가 새로 붙은 이슈만 요약한다.
   - 기사 문장을 그대로 옮기지 않고 3줄로 새로 쓴다.
   - AI는 점수를 매기지 않고 사실만 고른다: 사건 유형(기준표의 이름 중 하나, 응답 형식의 enum으로 강제), 직접 당사자 기업, 확정 여부. AI에게는 유형별 기본점을 보여주지 않는다.
   - 중요도는 `agent/score.py`가 `config/settings.yaml`의 기준표로 계산한다: 사건 유형 기본점 + 관심 기업 직접 당사자(+1) + 매체 3곳 이상 보도(+1) + 미확정(−1), 결과를 1～5로 맞춤. 계산식을 판단 근거로 남긴다.
   - 점수는 실행할 때마다 모든 이슈를 다시 계산한다. 그래서 기준표 숫자를 바꾸거나 다른 매체 기사가 붙으면 AI 호출 없이 바로 반영된다.
   - 사건 유형이 없거나 기준표에 없는 이슈(예전 방식으로 점수를 매긴 이슈, 유형 이름을 바꾼 경우)는 요약은 그대로 두고 헤드라인·요약·기사 제목으로 분류만 다시 한다.
5. **저장**: 임시 파일에 쓴 뒤 교체(원자적 쓰기)한다. 마지막으로 업데이트된 지 30일이 지난 이슈는 월별 보관 파일로 옮긴다.
6. **게시 원칙**: 공개 저장소와 웹에는 헤드라인, 매체명, 시각, 원문 링크, AI 요약, 태그, 중요도만 올린다. 기사 본문, RSS 요약문, 이미지는 올리지 않는다.

## 4. 데이터 구조

### `data/issues.json`

```json
{
  "version": 1,
  "updated_at": "2026-10-26T03:17:00Z",
  "issues": [
    {
      "id": "c20261026-0007",
      "headline": "삼성전자, 엔비디아에 HBM4 공급 확정",
      "summary": ["…", "…", "…"],
      "category": "메모리",
      "tags": ["HBM4", "엔비디아"],
      "companies": ["삼성전자", "엔비디아"],
      "event_type": "수주·공급",
      "confirmed": true,
      "parties": ["삼성전자", "엔비디아"],
      "importance": 5,
      "importance_reason": "수주·공급 3점, 관심 기업(삼성전자, 엔비디아) +1, 매체 4곳 보도 +1 → 5점",
      "status": "summarized",
      "region": "both",
      "first_seen": "2026-10-26T00:17:00Z",
      "updated_at": "2026-10-26T03:17:00Z",
      "articles": [
        {"key": "3f2a…", "title": "…", "url": "…", "source": "디일렉", "lang": "ko", "published_at": "…"}
      ]
    }
  ]
}
```

- `status`: `summarized`(요약 완료) 또는 `pending`(AI 오류로 요약 대기)
- `event_type`·`confirmed`·`parties`: AI가 고른 사실. `importance`·`importance_reason`은 이 값과 기사 매체 수로 코드가 계산한 결과
- `importance_raw`: 1～5점으로 맞추기 전 점수(기본점 + 가감점). 웹은 이 점수가 높은 순, 같으면 보도 시각(이슈의 가장 오래된 기사 발행 시각)이 최신인 순으로 정렬한다
- `region`: `ko`(국내 기사만), `en`(해외 기사만), `both`(둘 다)

### `data/state.json`

마지막 성공 시각, 이미 본 URL(14일), 매체별 상태(마지막 성공·연속 실패·마지막 새 기사 시각)를 담는다.

### `data/runs.json`

실행마다 수집 수, 거르기 후 수, 새 이슈 수, 요약 수, AI 호출 수, 토큰 사용량, 추정 비용(USD), 오류를 기록한다.

- `relevant`: 이번 실행에서 처리한 관련 기사 수. 상한 때문에 미룬 기사는 처리하는 실행에서 센다.
- `new_issues`(새로 만든 이슈 수)와 `summarized`(요약한 횟수)는 서로 다를 수 있다. 요약은 실행당 30건까지만 하고 나머지는 다음 실행에서 하며, 이미 요약한 이슈도 다른 매체 기사가 붙으면 다시 요약한다(`resummarized`).
- `pending`: 다음 실행에서 요약할 이슈 수. 요약에 3번 실패해 더 시도하지 않는 이슈는 `failed`로 따로 센다.

## 5. AI 사용 설계

| 호출 | 모델 | 횟수 | 입력 | 출력 (JSON 스키마) |
| --- | --- | --- | --- | --- |
| 이슈 묶기 ① 사건 정리·관련성 | 설정한 제공사·모델 | 20묶음마다 3회 (다수결. 실행당 최대 80묶음, 넘치면 다음 실행으로) | 기사 제목·요약문 200자 | 기사마다 `event`, `relevant` |
| 이슈 묶기 ③ 같은 사건 확인 | 같음 | 후보 짝 20개마다 3회 (2번 이상 같다고 한 짝만 묶음) | 짝의 두 기사 (기존 이슈는 헤드라인·처음 기사 제목 3건·요약 첫 문장) | 짝마다 `reason`, `same` (확실할 때만 true) |
| 요약·사건 분류 | 같음 | 이슈당 1회, 실행당 최대 30회 | 이슈의 기사 최대 4건 (각 1,500자) | headline, summary[3], tags, companies, event_type, confirmed, parties |
| 다시 분류 | 같음 | 분류가 필요한 이슈당 1회, 실행당 최대 30회 | 저장된 헤드라인·요약·기사 제목 | event_type, confirmed, parties |
| 사건 유형 확인 | 같음 | 기본점 4점 이상 유형을 고른 이슈마다 3회 (다수결, 아니면 그 유형을 빼고 다시 분류) | 헤드라인·요약·기사 제목, 유형 이름·설명 | reason, fits |

- **제공사 선택**: `config/settings.yaml`의 `provider`를 `openai`(기본) 또는 `claude`로 바꾼다. 제공사마다 다른 부분(호출 방법, 오류 종류, 사용량 표기)은 `agent/analyze.py`의 `OpenAIBackend` / `ClaudeBackend`에 있고, 프롬프트·응답 형식·검증은 공통이다.
- **구조화 출력**: 같은 Pydantic 모델(`agent/models.py`)을 OpenAI는 `client.responses.parse(text_format=…)`, Claude는 `client.beta.messages.parse(output_format=…)`로 강제한다.
- **비용 절감**: 같은 지시문을 반복해서 보내므로 프롬프트 캐싱을 쓴다 (OpenAI는 자동 + `prompt_cache_key`, Claude는 `cache_control`). Claude는 요청이 거절되면 서버가 다른 모델로 다시 시도하는 fallback도 켠다.
- **오류 구분**: 키·모델 문제와 크레딧 부족(OpenAI `insufficient_quota`, Claude 크레딧·한도 오류)은 그 실행의 AI를 멈추고, 거절·형식 오류·일시 오류는 그 호출만 실패로 처리한다.
- 기사 내용은 신뢰할 수 없는 입력이므로 AI에게 도구를 주지 않고, 지정한 JSON 형식으로만 답하게 한다.

## 6. 운영 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 예약 실행이 멈춤 (60일 무활동 규칙 등) | 웹에 "마지막 업데이트" 경고, 실패 메일, 45일에 한 번쯤 사람이 직접 커밋 |
| 응답이 멈춘 AI 요청 | 요청당 90초 제한, 실행당 AI 시간 15분 예산, 남은 요약은 다음 실행으로 |
| AI가 기사 문장을 그대로 옮김 | 코드에서 길이 제한 + 본문과 40자 이상 같은 구간이 있으면 거부 |
| RSS 끊김·차단 | 매체별 독립 처리, 상태 패널, 과반이 실패하면 실행 실패로 알림 |
| API 크레딧 소진·한도 초과 | AI 호출을 멈추고 "요약 대기"로 게시, 다음 회차 재시도 |
| 데이터 파일 손상 | 원자적 쓰기, 동시 실행 방지, push 실패 시 실행 실패 |
| 저작권 | 우리 요약 + 링크만 게시, 원문 미수집, 안내문, 검색엔진 비노출 |
